PROJETO: ANIME RPG DISCORD — SISTEMA PROFISSIONAL

Quero desenvolver um bot de RPG de animes para Discord, profissional, escalável e seguro, inspirado em sistemas de Anime Simulator/Tower Defense RPG.

TECNOLOGIAS
- TypeScript
- Node.js
- Discord.js v14
- PostgreSQL
- Neon Database
- Drizzle ORM ou Prisma
- Zod
- Pino
- Vitest
- ESLint
- Prettier

OBJETIVO
O jogador invoca personagens de diferentes animes, monta uma equipe de até 5 personagens e participa de batalhas automáticas por turnos.

1. PERSONAGENS
Cada personagem possui:
- ID
- Anime
- Nome
- Raridade
- Nível
- XP
- HP
- Ataque
- Defesa
- Velocidade
- Energia
- Chance crítica
- Dano crítico
- Skills
- Passiva
- Elemento/tipo
- Imagem
- Evolução

Raridades:
Comum, Incomum, Raro, Épico, Lendário e Mítico.

2. INVOCAR
Comandos:
 /invocar
 /invocar quantidade:1
 /invocar quantidade:10
 /banner

Criar:
- Chances por raridade
- Pity System
- Soft Pity
- Hard Pity
- Banner normal
- Banner limitado
- Banner de evento
- Histórico de invocações

As probabilidades devem ser configuráveis.

3. EQUIPE
O jogador pode possuir vários personagens, mas apenas 5 participam da equipe principal.

Comandos:
 /equipe
 /equipe adicionar
 /equipe remover
 /equipe trocar
 /equipe ordenar

A posição deve importar para estratégias de tanque, DPS, suporte, healer e controle.

4. COMBATE
O combate deve ser TURN-BASED AUTOMÁTICO.
O jogador não precisa clicar em cada ataque. O servidor calcula automaticamente as ações.

Cada batalha mostra:
- Equipe do jogador
- Inimigos
- HP
- Energia
- Rodada
- Iniciativa
- Últimas ações
- Recompensas

5. INICIATIVA
A ordem é calculada principalmente pela velocidade dos personagens, com pequena variação aleatória controlada.

6. IA
A IA decide automaticamente:
- Ataque básico
- Habilidade
- Ultimate
- Cura
- Buff
- Debuff
- Defesa
- Controle

Exemplos:
- HP abaixo de 40% → habilidade defensiva
- Inimigo abaixo de 20% → ultimate
- Energia >= 100 → priorizar ultimate
- Caso contrário → ataque básico

Cada personagem pode ter uma estratégia diferente.

7. SKILLS
Cada personagem possui:
- Ataque básico
- Habilidade 1
- Habilidade 2
- Ultimate
- Passiva

Tipos:
DAMAGE, HEAL, BUFF, DEBUFF, STUN, DOT, SHIELD, AOE, EXECUTE, REVIVE.

Cada skill pode ter:
- Dano
- Custo de energia
- Cooldown
- Alvo
- Efeitos

8. STATUS
Criar:
- Burn
- Shock
- Freeze
- Stun
- Poison
- Bleed
- Shield
- Attack Up/Down
- Defense Up/Down
- Speed Up/Down

Cada efeito possui tipo, duração, stacks, valor e origem.

9. ENERGIA
Cada personagem possui energia de 0 a 100.
Ataques básicos geram energia.
Skills gastam energia.
Ultimate normalmente exige 100.

10. BATTLE ENGINE
Usar uma máquina de estados:

WAITING
→ PREPARING
→ INITIATIVE
→ ROUND_START
→ CHARACTER_TURN
→ ACTION
→ DAMAGE
→ STATUS_PROCESS
→ DEATH_CHECK
→ NEXT_TURN
→ ROUND_END
→ VICTORY/DEFEAT

Não usar while(true) para controlar batalhas.

11. LOG DE COMBATE
Exemplo:
- R1 • Personagem A • Ataque básico → Ninja Médico • dano 88
- R1 • Ninja Médico • Cura → Boss • +70 HP
- R2 • Personagem B • Habilidade Especial • dano 142
- R2 • Sistema • Escudo destruído
- R2 • Personagem D • Ataque básico → Ninja Médico • dano 105
- R2 • Sistema • Ninja Médico derrotado

12. SNAPSHOTS
Salvar snapshots contendo:
- battleId
- rodada
- turno
- timestamp
- estado da equipe
- estado dos inimigos
- ações

Isso permite histórico, replay, debug, auditoria e recuperação.

13. SEGURANÇA
O objetivo é uma arquitetura robusta, sem prometer segurança absoluta.

Proteger contra:
- SQL Injection
- Command Injection
- Manipulação de IDs
- Abuso de interactions
- Race Conditions
- Duplication Bugs
- Double Rewards
- Spam
- Manipulação de batalha
- Manipulação de moedas
- Replay de interações
- Requests duplicados
- Dados inconsistentes

Nunca confiar em dados enviados pelo usuário. Validar tudo no servidor.

14. BANCO NEON
Usar PostgreSQL no Neon.

Tabelas sugeridas:

user_characters

Usar Foreign Keys e índices.

15. ECONOMIA
Moedas:
- Gold
- Gems
- Tickets

Toda alteração importante deve gerar uma transação.
Registrar:
- userId
- tipo
- quantidade
- moeda
- origem
- referenceId
- data

16. ANTI-DUPLICAÇÃO
Recompensas devem possuir chave idempotente.
Antes de entregar:
- verificar se já foi processada
- se sim, não entregar novamente
- se não, registrar e entregar

17. TRANSAÇÕES
Operações críticas devem usar transaction:
- verificar usuário
- verificar recursos
- consumir recursos
- realizar ação
- salvar resultado
- registrar histórico
- commit
- rollback em caso de erro

18. IDEMPOTÊNCIA
Proteger operações como:
 /invocar
 /batalha
 /recompensa
 /daily

19. RATE LIMIT
Criar rate limit por usuário, guild, comando e interaction.
Proteger Buttons e Select Menus contra spam.

20. BATALHA SEGURA
O cliente/Discord nunca decide:
- Dano
- Recompensa
- XP
- Vitória
- Derrota
- Crítico
- RNG
- Energia
- HP

Tudo é calculado no servidor.

→ estado salvo no banco
→ bot voltou
→ Battle Recovery
→ batalha continua

Começar somente pela FASE 1. Entregar código completo e funcional antes de avançar.
